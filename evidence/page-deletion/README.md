# Page deletion

The measurement behind issue #180, for #174's last acceptance: deleting a
page costs the references to it, not a walk of the document (DESIGN.md
section 8, F4).

## Workload

Documents of 1,000 to 64,000 pages in one flat page tree, generated by
`measure.py`:

- Untagged: pages alone.
- Tagged: each page has one structure element that marks its content, and
  the parent tree maps the page back to it.
- Linked: 4,000 pages, with 0 to 10,000 link annotations on the first page
  that lead to the middle page.

Each row is the median of 7 rounds of deleting the middle page
(`del doc.pages[i]`), or of keeping every page except the middle one in reverse order
(`doc.pages.select`):

- First: on a newly opened document. This includes building the
  document's reference index, which walks every object once; later
  versions derive it from their change sets (#173).
- Repeated: the same edit after undoing the first.

## Running

```sh
uv run python evidence/page-deletion/measure.py
```

## Reviewed results

`results/review-macos-arm64.md` records the reviewed implementation and
measurement time. The same script and seven-round protocol give:

- With 4,000 pages, repeated deletion is 3.12 ms without links and
  15.19 ms with 10,000 links, about 1.2 microseconds per additional link.
- With 64,000 pages, repeated deletion is 54.27 ms untagged and 164.77 ms
  tagged. Selection is 66.44 ms and 175.30 ms respectively.
- Page-list rewriting, reference updates, garbage collection, and the
  current whole structure-tree traversal still contribute work that grows
  with document size. This measurement does not establish the stronger
  claim that the complete operation costs only incoming references.
  #184 addresses structure planning; the page list remains linear.

The reviewed stack includes charged copying, reference-generation checks,
writer-lock ordering, and collection of unreachable cycles. These figures
are an end-to-end remeasurement, not an isolated timing of any one fix.
The historical 10 ms figure below does not describe the reviewed head.

## Original results

`results/macos-arm64.md` preserves the original run:

- Links: a repeated deletion costs about 0.9 µs per link to the deleted
  page, 1.6 ms with none and 10 ms with 10,000. Before this measurement,
  the rules searched the annotations array again for each link and removed
  its entries one at a time, 816 ms for 10,000 links; they now read each
  holder of references once and remove an array's entries in one pass.
- Size, untagged: a repeated deletion costs about 0.4 µs per page of the
  document, 27 ms at 64,000 pages. That is the page list: a page edit
  writes the root of the page tree with every page as a kid and rebuilds
  the page index, whatever refers to the removed page.
- Size, tagged: a tagged document adds about 1.1 µs per structure element,
  72 ms at 64,000 elements, because the structure rule (#179) walks the
  whole structure tree as pylopdf's does. #184 plans it from the references
  to the removed pages instead.
- First deletions add about 1.6 µs per object for the reference index.
