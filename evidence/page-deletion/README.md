# Page deletion

The measurement behind issues #180 and #184, for #174's last acceptance:
deleting a page costs the references to it, not a walk of the document
(DESIGN.md section 8, F4).

## Workload

Documents of 1,000 to 64,000 pages in one flat page tree, generated by
`measure.py`:

- Untagged: pages alone.
- Tagged, flat: each page has one structure element that marks its
  content, a kid of the structure tree root, and one parent tree leaf maps
  every page back to its element.
- Tagged, nested: the same elements in sections of 64, and the parent tree
  in leaves of 64 pages under one node, as producers commonly write them.
- Linked: 4,000 pages, with 0 to 10,000 link annotations on the first page
  that lead to the middle page.

Each row is the median of 7 rounds of deleting the middle page
(`del doc.pages[i]`), or of keeping every page except the middle one in reverse order
(`doc.pages.select`):

- First: on a newly opened document. This includes building the
  document's reference index, which walks every object once; later
  versions derive it from their change sets (#173).
- Repeated: the same edit after undoing the first.

## Running

```sh
uv run python evidence/page-deletion/measure.py
```

## Reviewed structure-planning comparison

The result files record exact implementation and script identifiers:

- `results/review-structure-before-macos-arm64.md`: reviewed #185, whole structure walk.
- `../reference-collection/results/after-macos-arm64.md`: #324 collector
  boundaries with the same whole walk (relative to `evidence/page-deletion/`).
- `results/review-structure-final-macos-arm64.md`: targeted structure planning plus
  #324. Its original workload tables are unchanged; the script additionally
  measures unrelated structure at a fixed page count.
- `results/review-structure-after-macos-arm64.md` preserves the intermediate targeted
  run before #324, including the collector cost that motivated that follow-up.

Reproduce a run by using its script with `uv run python` in the corresponding
implementation checkout. The earlier before run used the already-built
reviewed #185 extension before rebuilding #186.

At 64,000 pages, median repeated deletion after undo is:

| Workload | Reviewed #185 | Collector boundaries only | Final targeted planning |
| --- | ---: | ---: | ---: |
| Untagged | 58.14 ms | 50.10 ms | 51.58 ms |
| Flat tagged | 171.87 ms | 154.05 ms | 117.21 ms |
| Nested tagged | 134.44 ms | 125.29 ms | 61.53 ms |

The nested result is now close to the untagged page-list cost. The remaining
page-key and annotation scans scale with page count. Flat trees still require
rewriting their large root child array and parent-tree leaf. These timings do
not claim that rewriting the complete page list is independent of its size.

The additional workload separates unrelated structure size from page count:
three pages, one removed element, and 0 to 64,000 unrelated elements below a
retained subtree with a separate parent-tree leaf. Repeated deletion remains
0.02 to 0.06 ms; the first deletion grows to 88.57 ms because it builds the
complete reference index. A Rust read-set regression independently confirms
that targeted planning does not read an unrelated structure element, while
the full traversal does. The collector's 10,000-object budget regression proves
that liveness propagation also avoids the retained subtree.

`results/review-macos-arm64.md` preserves the earlier reviewed #185 workload:
3.12 ms without links and 15.19 ms with 10,000 links on 4,000 pages; 54.27 ms
untagged and 164.77 ms flat tagged for 64,000 pages. Different runs have normal
measurement variation. These are end-to-end timings, not isolated timings of
a single safety fix, and the historical 10 ms figure below is not current.

## Original results

`results/macos-arm64.md` preserves the original run:

- Links: a repeated deletion costs about 0.9 µs per link to the deleted
  page, 1.6 ms with none and 10 ms with 10,000. Before this measurement,
  the rules searched the annotations array again for each link and removed
  its entries one at a time, 816 ms for 10,000 links; they now read each
  holder of references once and remove an array's entries in one pass.
- Size, untagged: a repeated deletion costs about 0.4 µs per page of the
  document, 27 ms at 64,000 pages. That is the page list: a page edit
  writes the root of the page tree with every page as a kid and rebuilds
  the page index, whatever refers to the removed page.
- Size, tagged: the structure rule (#179) walked the whole structure tree
  as pylopdf's does, 71 ms more than untagged for a repeated deletion at
  64,000 pages, nested, and 103 ms in all; #184 walks only the elements
  that refer to the removed pages, their ancestors, and the parent tree
  leaves that name them, from the reference index. A repeated deletion now
  costs 33 ms nested, 4 ms more than untagged: the scans of the pages for
  their parent tree keys and annotations, which the page list's cost
  already bounds. Flat, it costs 77 ms, down from 103 ms: the root's `/K`
  and the one parent tree leaf hold every page, and a deletion rewrites
  both.
- First deletions add about 1.6 µs per object for the reference index.
